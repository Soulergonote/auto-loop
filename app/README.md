# Auto-loop : interface

Petite application web pour ouvrir ou fermer une position à levier sur Aave v3 ou Morpho Blue (voir plus bas) en **une transaction**, sur Ethereum (marchés Core et Prime), Arbitrum, Base, Avalanche, Optimism, Polygon, BNB Chain, Mantle, Plasma, Linea, Sonic, Monad et MegaETH, via le contrat `LeverageExecutorV2` (`../contracts` ; un contrat v1 déjà déployé reste reconnu et utilisé). On choisit la paire collatéral / dette et le levier ; le swap passe par Velora, KyberSwap ou 1inch selon la chaîne ; l’interface calcule l’emprunt, demande un devis avec le contrat comme taker, affiche le health factor projeté, puis fait signer.

Stack : Vite + React + TypeScript, wagmi 2 / viem 2.

## Lancer

```bash
npm install
cp .env.example .env.local     # puis remplir
npm run dev                    # http://localhost:5173
npm test                       # tests des calculs
VITE_DEMO=true npm run dev     # données de marché fictives, sans RPC
npm run build                  # site 100 % statique dans dist/, à servir depuis n'importe quel dossier
```

Le build ne dépend d'aucun serveur : le navigateur appelle directement l'API Velora (`api.paraswap.io`, CORS ouvert) et le RPC public de Base. `dist/` peut donc être hébergé tel quel (GitHub Pages, IPFS…). Les variables `VITE_*` sont figées au moment du build.

| Variable | Rôle |
|---|---|
| `VITE_EXECUTORS` | Adresse du contrat déployé pour chaque marché, en JSON (`{"base":"0x…"}`) : un contrat par pool Aave. Marché absent : l'app propose de **déployer le contrat v2 depuis le portefeuille connecté** (bouton « Déployer le contrat », routeurs = agrégateurs qui cotent sur la chaîne, prêteur gratuit = Morpho Blue là où il existe), ou de coller l'adresse d'un contrat déjà déployé ; l'adresse est retenue dans le navigateur. Toute adresse, d'ici ou du navigateur, n'est utilisée qu'après vérification on-chain que son code est exactement celui du contrat (v2, ou v1 pour un contrat déjà déployé) pour ce Pool. Avec un contrat v1 enregistré dans le navigateur, un bandeau propose de déployer la v2. `VITE_EXECUTOR_ADDRESS` reste lue pour Base. |
| `VITE_RPC_URL_<chainId>` | RPC d'une chaîne pour les lectures et simulations (vide = PublicNode, puis le RPC public de la chaîne). `VITE_RPC_URL` vaut pour Base. Pour un fork local : `anvil --fork-url https://mainnet.base.org --chain-id 8453` puis `http://127.0.0.1:8545`. |
| `VITE_QUOTE_MODE` | `auto` (API réelles, repli sur un devis simulé si elles ne répondent pas), `live` ou `mock`. Un devis simulé n’est jamais exécutable. |
| `VITE_VELORA_INCLUDE_DEXS`, `VITE_VELORA_EXCLUDE_DEXS` | Listes de DEX (noms Velora, séparés par des virgules) autorisés ou exclus des routes. Vide = toutes les routes. Sert surtout au test sur fork (voir plus bas). |
| `VITE_DEMO` | `true` : prix et paramètres fictifs, pour voir l’interface sans réseau. |

## Contrat commun à adresse prévisible

Depuis le 12/11/2026, le contrat d'un réseau (v2 pour un marché Aave, `LeverageExecutorMorpho` pour Morpho) est déployé par CREATE2 à travers le déployeur déterministe `0x4e59b44847b379578588920cA78FbF26c0B4956C` (présent sur les 16 réseaux de l'app, relevé avec `npx vite-node e2e/probe-create2.ts`), avec un sel fixe (`keccak256("auto-loop")`, `src/chain/create2.ts`). L'adresse ne dépend que du code et des arguments du constructeur (pool, routeurs, prêteurs) : tous les utilisateurs de l'app ont la même. L'app regarde d'abord s'il y a du code à cette adresse ; si oui, et que le contrôle de code passe, elle l'utilise sans rien demander (« contrat commun, même adresse pour tous ») ; sinon le bouton du résumé le déploie, une fois pour tout le monde. Un contrat v1 (ou v2 sans Pendle) enregistré dans le navigateur reste utilisé ; le bandeau propose « Utiliser le contrat commun » dès que celui-ci existe. Sans déployeur sur un réseau, déploiement classique. Les contrats n'ont pas de propriétaire et n'agissent que pour l'adresse qui signe : partager un contrat ne donne aucun droit à personne. Après un vrai déploiement, `contracts/script/verify-sourcify.sh` publie le source sur Sourcify (noms et décodage des appels dans Blockscout et Rabby). Testé le 12/11/2026 sur fork de Base : déploiement par le bouton (transaction vers le déployeur, contrat à l'adresse calculée), puis, dans un navigateur neuf sans adresse enregistrée, contrat commun trouvé et ouverture 3x de 1 WETH. Passage d'une position v1 à la v2, testé le 12/11/2026 sur fork de Plasma (le cas réel : USDe / GHO) : ouverture 4x de 1 000 USDe avec un contrat v1, puis bouton « Déployer le contrat v2 » du bandeau (contrat à l'adresse commune calculée), puis fermeture totale de la même position par la v2. Rien à migrer : la position est sur le compte Aave, pas dans le contrat. Plasma n'ayant pas Morpho Blue dans l'app, la v2 y paie encore la prime de flash loan d'Aave (0,05 %).

## Interface

Les règles d’interface (agencement, couleurs, typographie, composants, ton, formats des nombres) sont fixées dans la charte UI/UX du projet ; tout écran la suit. En pratique : l’écran Boucle a les choix à gauche et un résumé fixe à droite avec l’unique bouton principal (barre collée en bas sur mobile) ; les réglages rares (agrégateur, slippage, durée, eMode) sont dans un bloc « Réglages » replié ; les formats passent tous par `src/ui/format.ts` et les couleurs des valeurs par `src/ui/tone.ts` (seuils du health factor propres aux paires corrélées : rouge sous 1,03, ambre sous 1,08, contre 1,1 et 1,3 sinon).

**Scanner, colonnes** : « Écart » = rendement du collatéral (taux de dépôt + rendement propre du token, ou APY fixe d'un PT) moins coût de l'emprunt (moins le rendement propre d'une dette qui en a un), sans levier ni bonus. « Détail » sur une ligne montre l'APY net jambe par jambe (rendement × levier, − emprunt × (levier − 1), + Merkl). Les marchés Morpho d'une même paire sur un même réseau (autre LLTV, autre oracle) sont regroupés sous la meilleure ligne (« + N marchés »), les autres dans le détail avec leur oracle (`src/features/scanner/scanGroups.ts`).

**Scanner, montant** (`src/domain/irm.ts`, `src/features/scanner/sizing.ts`) : un montant en dollars (« 25k », « 1,5 M ») recalcule chaque paire à cette taille. Taux juste après la boucle : Aave par la courbe de la réserve (`getInterestRateDataBps` de la stratégie v3.2+, gardée seulement si elle redonne le taux on-chain du moment ; utilisation = dette / (liquidité + dette)), la dette ajoutée monte le taux d'emprunt, le collatéral ajouté baisse son taux de dépôt ; Morpho par l'AdaptiveCurveIRM (courbe ×4 au-dessus de 90 % d'utilisation, ×1/4 à vide, taux cible déduit du taux et de l'utilisation du moment, sa dérive dans le temps non comptée). « avant : » montre l'APY sans cet effet ; « Gain / an » ; « rentable en N j » paie une estimation des swaps d'entrée et de sortie de l'emprunt au slippage par défaut de la paire. Une paire dont la capacité est sous le montant passe en fin de liste, grisée. « Ouvrir » préremplit le capital (montant converti en collatéral au prix de l'oracle, Aave).

**Arrivée sur la Boucle et filtres** (`src/features/scanner/prefs.ts`) : la Boucle d'un réseau s'ouvre sur la dernière paire choisie sur ce réseau dans ce navigateur ; sinon sur la meilleure paire corrélée du Scanner pour ce réseau (APY net positif, au moins 50 000 $ de capacité), au levier du health factor visé du Scanner et dans le meilleur eMode ; sinon WETH / USDC. Les filtres du Scanner (protocole, réseau, health factor, type de paire, APY négatifs) sont retenus dans le navigateur et écrits dans l'adresse (`#scanner?protocole=aave&reseau=9745&hf=1.2&paires=stables&negatifs=1`) : un lien partagé rouvre la même vue.

**Slippage** (`src/domain/slippage.ts`) : par défaut selon la paire, tant qu'on n'en choisit pas un dans « Réglages » (marqué « auto ») : 0,05 % entre deux stablecoins USD, 0,1 % entre actifs corrélés (wstETH / WETH), 0,3 % sinon et pour une route Pendle (PT), 0,3 % aussi pour la revente des rewards. Choix possibles : 0,01, 0,05, 0,1, 0,3 et 1 %. Quand une transaction échoue parce que le swap a rendu moins que son minimum, le message d'erreur propose le cran suivant, avec ce qu'il peut coûter au pire en dollars (ouvrir, fermer) ; l'app recote, puis il faut signer à nouveau.

## Marchés

Liste dans `src/config/aave.ts` (`MARKETS`), adresses des pools tirées de `@bgd-labs/aave-address-book`. Les actifs de chaque marché sont lus sur la chaîne (`getReservesList`), donc un nouvel actif listé par Aave apparaît sans changer le code. Chaque agrégateur n'est proposé que sur ses chaînes (`chains` dans `AGGREGATORS`) : Velora ne couvre ni Mantle, ni Plasma, ni Linea, ni Monad, ni MegaETH, ni HyperEVM, KyberSwap prend alors le relais. Sur Morpho, un collatéral que l'API ne cote pas (parts de vault comme steakEURCV, certains PT) est valorisé au prix de l'oracle du marché fois celui du jeton emprunté, sinon il sortait du Scanner. MegaETH (ajouté le 11/11/2026) : pool de l'address book Aave, RPC injoignable depuis l'environnement de dev, donc non relu sur la chaîne avant mise en ligne. KyberSwap est appelé sans clé (en-tête `x-client-id: auto-loop`) ; un devis qui contient des frais (`extraFee`) est refusé.

**1inch** (remis le 12/11/2026) : Swap API v6.0, sur tous les réseaux de l'app sauf Plasma et MegaETH (l'API y répond 404). Routeur AggregationRouterV6, à une autre adresse sur HyperEVM et Arc (lue sur `approve/spender`, code vérifié sur chaque chaîne). L'API demande une clé : `VITE_ONEINCH_API_KEY`, injectée au build depuis le secret GitHub `ONEINCH_API_KEY` du dépôt. Elle est donc lisible dans le site publié : c'est une clé gratuite dont le seul risque est le quota (la régénérer sur le portail 1inch si elle est abusée). Sans clé, 1inch n'est pas proposé. Les appels sont espacés de 1,1 s (offre gratuite : 1 requête/s). Aucun frais demandé ; seule la méthode générique `swap` est acceptée, et son calldata est relu pour les échanges depuis le portefeuille. Les nouveaux contrats autorisent le routeur 1inch ; un contrat déployé avant reste valide, et l'app ne cote simplement pas 1inch pour lui (lecture de `isRouterAllowed`). Ajouter 1inch a changé l'adresse CREATE2 des contrats partagés sur ses réseaux.

**SparkLend** (ajouté le 13/11/2026) : fork d'Aave v3.1 sur Ethereum, branché comme un marché de plus (`fork: 'Spark'` dans `MARKETS`), affiché « Spark » dans le Scanner, les positions et le sélecteur de marché d'Ethereum. Deux différences gérées : les eModes se lisent à l'ancienne (`getEModeCategoryData`, catégorie dans les bits 168–175 de la configuration de chaque réserve) quand les lectures v3.2 échouent, et le Pool refuse le flash loan ouvert en dette (`FLASHLOAN_INTO_BORROW_DEPRECATED`). Le contrat v2 emprunte donc dans le rappel du flash loan quand le pool ne prend pas de prime (voir le README du contrat) ; sur Spark, seul le contrat v2 actuel est reconnu. Testé sur fork d'Ethereum depuis l'app : déploiement, ouverture wstETH/WETH 5x, fermeture complète. SparkLend Gnosis est écarté : toutes ses réserves sont gelées.

## Rewards Merkl

Les APY ajoutent les campagnes Merkl en cours sur Aave (`api.merkl.xyz/v4/opportunities`, sans clé) : rewards de dépôt sur l'aToken du collatéral, rewards d'emprunt sur le jeton de dette. Une campagne n'est comptée que si elle nomme l'adresse de l'aToken ou du jeton de dette ; sinon elle est ignorée. Les conditions d'éligibilité propres à certaines campagnes ne sont pas vérifiées. Si l'API ne répond pas, l'interface le dit et affiche les APY sans bonus.

## Rendement propre des tokens

Les APY comptent aussi le rendement propre des tokens à rendement (wstETH, weETH, sUSDe, syrupUSDC, sUSDS, sDAI…), qu'Aave et Morpho intègrent au prix mais n'affichent pas comme un taux. Il est pris à la source la plus récente qui connaît le token (`src/services/yield/tokenYield.ts`), dans cet ordre :

1. taux publié on-chain par le contrat du token (sDAI : DSR, sUSDS : SSR, stUSDS : STR) ;
2. hausse du prix de part d'un coffre ERC-4626 sur 7 jours (`convertToAssets` maintenant et 7 jours avant, lu par un RPC d'archive sans clé, `ARCHIVE_RPCS` dans `src/config/rpc.ts`) pour les coffres qu'aucune API ne suit : savUSD, wsrUSD, syrupUSDG, yoUSD ;
3. rendement sous-jacent que montre l'API Pendle quand Pendle a un marché sur le token ;
4. rendement de l'actif dans l'API Morpho ;
5. pour une réserve Aave, à défaut : l'adaptateur de prix « CAPO » d'Aave (`getSourceOfAsset` sur l'oracle), dont la hausse entre le relevé (`getSnapshotRatio`, `getSnapshotTimestamp`) et le taux actuel (`getRatio`), annualisée, donne une moyenne parfois sur plusieurs mois (`src/services/yield/nativeYield.ts`, relevé de moins de 7 jours ignoré).

Un token qui existe sur plusieurs chaînes (syrupUSDC sur Base, Arbitrum et Arc, sUSDe OFT…) prend le rendement trouvé pour une autre copie quand aucune source ne le connaît sur sa chaîne. Les copies sont trouvées automatiquement (`src/services/yield/copies.ts`) : même symbole et même prix à 0,5 % près (DefiLlama, sinon API Morpho) qu'un token connu sur une autre chaîne, donc un nouveau réseau ou un nouveau pont ne demande rien. Le prix écarte les imitations, et une erreur ne changerait qu'un rendement affiché, jamais une transaction. Seuls les taux on-chain et les vaults sans API sont listés à la main dans `src/services/yield/yieldTokens.ts` ; une valeur nulle ou au-dessus de 100 % est ignorée. L'écran indique la source sous les taux (« Taux Aave », détails du marché Morpho). Le rendement s'ajoute sur le collatéral (× levier) et se retranche sur une dette qui en a un (× levier − 1). Un PT Pendle compte son APY implicite, fixe jusqu'à l'échéance (voir plus bas). Sans aucune source, le Scanner étiquette « rendement du token non compté » un token dont le prix laisse penser qu'il en a un (au 12/11/2026 : wstUSR, dont le taux ne bouge plus depuis 30 jours, USR ayant perdu son ancrage à environ 0,03 $).

## Boucles Pendle PT

Réseaux : tous ceux de l'app où Pendle est déployé, soit Ethereum (Core et Prime), Arbitrum, Base, Optimism, BNB Chain, Mantle, Plasma, Sonic et Monad (adresses du dépôt pendle-core-v2-public, relevées le 09/11/2026 ; pas de Pendle sur Avalanche, Polygon ni Linea). Le 09/11/2026, seuls Plasma et Monad listent des PT actifs sur Aave v3 ; les autres réseaux les proposeront dès qu'Aave en listera. Avant d'ouvrir, l'app cote aussi la sortie (PT → actif de la dette, à la taille de la position) : si aucun agrégateur ne revend le token que rend le SY, l'ouverture est bloquée, car la position ne pourrait être fermée ni avant ni après l'échéance.

Un PT Pendle listé sur Aave (en eMode seulement, LTV 0 hors eMode) se boucle comme un autre collatéral, avec un rendement fixe jusqu'à son échéance (`src/protocols/pendle/pt.ts`). Lectures : `SY()`, `YT()`, `expiry()`, `isExpired()` du PT, son marché Pendle (liste de `PENDLE_MARKETS` et API Pendle, chaque marché vérifié par `isValidMarket` des factories), APY implicite `exp(lastLnImpliedRate) − 1`, TWAP 15 min de l'oracle PY. Devis par le RouterStatic (`swapExactTokenForPtStatic`, `swapExactPtForTokenStatic`, `redeemPyToTokenStatic` après échéance) et calldata du routeur Pendle v4 construite par l'app, relue avant signature (destinataire, marché, token, montant, minimum). Route en plusieurs étapes du contrat v2 : USDC → token d'entrée du SY (KyberSwap ou Velora) → PT (Pendle), et l'inverse à la fermeture ; après échéance, rachat 1 pour 1 du PT (et une fermeture totale rachète tout le PT, le reste revient en dette). Il faut un contrat v2 qui autorise le routeur Pendle : un contrat déployé avant n'est pas refusé, un bandeau propose d'en déployer un nouveau.

Écrans : tuiles « APY fixe » (rendement au prix payé, jusqu'à l'échéance) et « Échéance » (jours restants, APY coûts compris sur cette durée) dans Ouvrir ; health factor projeté à l'échéance (le prix d'oracle remonte vers 1, la dette grossit) dans Risques ; bloc « Prix du PT » (oracle Aave, prix payé, marché Pendle, TWAP) ; « Coût de sortie » dans Fermer ; étiquette « PT · J−N » dans le Scanner (un PT échu ou sans marché Pendle n'y figure pas) ; tuile « Échéance du PT » et bouton « Renouveler » dans Positions.

**Renouveler** (dernier mois avant l'échéance, ou PT échu) : vers un PT plus long accepté par l'eMode du compte, même sous-jacent d'abord. En une transaction (`swapCollateral` : flash loan du nouveau PT, dépôt, retrait et vente de l'ancien) quand Aave ou Morpho peut prêter le nouveau PT ; Aave liste les PT récents sans flash loan, le renouvellement passe alors en deux transactions : fermer (le PT restant revient au portefeuille), puis ouvrir le nouveau PT au même levier avec ce PT comme capital, prérempli. Entre les deux, aucune position n'est ouverte.

Test sur fork d'Ethereum (`NET=ethereum bash e2e/fork.sh` liste PT-reUSDe-10DEC2026 et PT-sUSN-22JUL2027 sur Aave Core avec `contracts/script/ForkListPt.s.sol`, oracle à décote linéaire, `DISCOUNTS="1500,800"` en bps pour la régler ; puis `MARKET=ethereum CHAIN_HEX=0x1 COLL=PT-reUSDe-10DEC2026 CAPITAL=USDC AMOUNT=1000 LEV=5 node e2e/run.cjs open o`, `run.cjs roll2 r` pour le renouvellement en deux temps, `CLOCK=<s>` avance l'horloge de la page comme `evm_increaseTime`). Fork de Base : `NET=base-pendle bash e2e/fork.sh` liste PT-yUTY-17DEC2026 contre USDC ; testé le 09/11/2026 : ouverture x4 avec 1000 USDC, achat direct par Pendle ; la fermeture n'a pas de route yUTY → USDC sur le fork (sources limitées), ce qui a motivé le contrôle de sortie. Arbitrum : `NET=arbitrum` (PT-sUSDai) demande un RPC d'archive (`FORK_URL`), PublicNode ne garde pas assez de blocs.

Testé le 08/11/2026 : ouverture x5 (USDC → reUSDe par KyberSwap → PT par Pendle), écran Positions, renouvellement en deux temps reUSDe → sUSN (fermeture, puis ouverture avec 970 PT-reUSDe comme capital : Pendle + Velora + Pendle), fermeture après échéance par rachat. Limite du fork : après un `evm_increaseTime`, les devis Velora et KyberSwap portent l'échéance de l'heure réelle et revertent (« Transaction too old ») ; seule une route 100 % Pendle passe.

## Morpho Blue

Réseaux : Ethereum, Base, Arbitrum, Optimism, Polygon, Arc, Unichain, HyperEVM, Monad, Robinhood Chain et MegaETH (Unichain, HyperEVM et Monad ajoutés le 11/11/2026, Robinhood Chain le 12/11/2026 : réseaux où un agrégateur cote et où l'API Morpho liste des marchés ; BNB, Linea, Sonic, Etherlink et MegaETH ont Morpho mais l'API les refuse ; Katana, Stable et Tempo sont dans l'API mais aucun agrégateur n'y cote ; World Chain et X Layer n'ont aucun marché listé), dans le même sélecteur « Réseau » (groupe « Morpho Blue »). Contrat : `LeverageExecutorMorpho` (`../contracts`), un par réseau, déployé depuis le portefeuille avec le bouton « Déployer le contrat Morpho » (routeurs : agrégateurs du réseau et Pendle) ou collé puis vérifié comme les autres (code on-chain identique au déploiement simulé, `src/chain/deploy.ts`). Adresse retenue dans le navigateur sous l'id `morpho-<réseau>`.

**Marchés** (`src/protocols/morpho/markets.ts`) : liste de l'API Morpho (`blue-api.morpho.org/graphql`, CORS ouvert, sans clé), marchés listés par Morpho par défaut, case « Inclure les marchés non listés » pour ceux qui ont au moins 10 000 $ déposés. L'API ne fait que lister et classer : avant d'afficher une position ou de faire signer, l'app relit le marché sur Morpho (`idToMarketParams` doit redonner exactement l'oracle, l'IRM et la LLTV annoncés, l'id est recalculé), le prix de l'oracle du marché, le taux de l'IRM (`borrowRateView`) et la position (dette en parts arrondie au-dessus comme Morpho, intérêts courus compris). Bandeaux : marché non listé, oracle « Unknown », alertes rouges de l'API. Rendement du collatéral : APY implicite Pendle pour un PT, rendement de l'API sinon ; rewards d'emprunt comptés par l'API.

**Marchés lus sur la chaîne** (`src/protocols/morpho/onchain.ts`, ajouté le 13/11/2026) : sur un réseau que l'API refuse, la liste vient de Morpho lui-même. Les ids viennent des événements `CreateMarket` depuis le déploiement de Morpho (RPC du réseau, sans clé, CORS ouvert ; par tranches si le RPC plafonne la plage), retenus dans le navigateur : la visite suivante ne lit que les blocs plus récents. Chaque marché est lu en trois multicalls (`idToMarketParams`, `market`, prix de l'oracle, taux de l'IRM, symboles), prix en dollars par DefiLlama, sinon prix de l'oracle fois celui du jeton emprunté. Gardés : marchés d'au moins 10 000 $ déposés dont les paramètres redonnent l'id. Morpho ne tient pas le total de collatéral par marché : il est remplacé par le minimum que la dette exige (dette / LLTV) pour classer, et l'écran montre l'encours emprunté. Ces marchés ne sont revus par personne : bandeau « Marché lu sur la chaîne », étiquette « non listé » dans le Scanner, pas de « Gain réel » (l'historique vient de l'API). Réseau couvert : MegaETH (wiTRY / USDm, 511 k$ déposés au 13/11/2026, vérifié en direct : marché, devis KyberSwap, écran d'ouverture). Écartés le 13/11/2026 : Sonic (15 marchés, tous sous 100 $), Linea (seul le marché vide de Morpho), BNB et Avalanche (aucun RPC sans clé ne sert leurs anciens journaux), Plasma (pas de Morpho Blue).

**Écrans** : Ouvrir / augmenter (capital dans le collatéral ou l'actif prêté, levier jusqu'au health factor 1,02), Fermer / réduire, Changer de marché (même actif prêté ; « Renouveler » quand le PT est dans son dernier mois : PT plus long de la même famille d'abord). Health factor et liquidation au prix de l'oracle du marché et à la LLTV, comme Morpho les calcule ; prêt flash gratuit. Le Scanner ajoute chaque marché listé, au levier du health factor visé (étiquette « Morpho · LLTV »). Positions lit les positions de l'adresse sur tous les marchés listés en un multicall (une position qui vient d'être ouverte apparaît sans attendre l'API), plus celles que l'API connaît sur des marchés non listés, et les compte dans le total.

**Refinancer Aave ↔ Morpho** (onglet « Refinancer », ajouté le 13/11/2026, `src/features/loop/morpho/MorphoRefinancePanel.tsx`, `src/protocols/morpho/refinance.ts`) : la même paire passe d'Aave v3 au marché Morpho affiché, ou l'inverse, en une transaction (`refinance` du contrat Morpho, prêt flash Morpho gratuit, sans swap). L'écran lit les pools Aave du réseau : chaque position Aave de la paire peut venir sur ce marché, la position Morpho peut partir vers chaque pool qui prête l'actif contre ce collatéral. Il compare taux d'emprunt (récompenses déduites, Merkl côté Aave), rendement du collatéral (Aave le prête, Morpho non), seuil de liquidation et liquidité, et donne health factor, APY net et écart par an aux taux du jour. Contrôles : liquidité du marché Morpho, liquidité et plafonds d'Aave, LTV d'Aave pour l'emprunt, health factor de ce qui reste sur le compte Aave. Un compte Aave vide passe d'abord dans le meilleur eMode de la paire ; un compte déjà utilisé garde le sien. Autorisations : aToken (vers Morpho) ou délégation d'emprunt (vers Aave), exactes dans un lot atomique et rendues à leur valeur après, sinon un message signé (permit ou `delegationWithSig`) en plus des deux signatures Morpho. Un ancien contrat Morpho (avant le refinancement) reste utilisable pour le reste ; l'onglet propose alors le contrat commun à jour (l'utiliser s'il existe, sinon le déployer).

**Autorisation** : Morpho demande que l'adresse autorise le contrat pour emprunter et retirer en son nom. L'app la donne le temps d'une seule transaction : avec un portefeuille qui envoie des lots atomiques (EIP-5792), autoriser → appeler → retirer l'autorisation dans le même lot ; sinon deux messages signés sans gas (autorisation au nonce n, retrait au nonce n + 1) que le contrat consomme au début et à la fin de l'appel. Une autorisation permanente trouvée sur le compte est signalée avec un bouton « Retirer l'autorisation ». Garde à chaque appel : health factor minimum (98 % du pire cas) et échéance de 20 minutes.

**Arc** (ajouté le 10/11/2026) : gas payé en USDC, KyberSwap seul agrégateur, pas de Pendle ; Morpho à l'adresse de la liste officielle de Morpho (même code que sur Ethereum, au séparateur de domaine EIP-712 près, comparé le 10/11/2026). ## Décomposition de l'APY

Le bloc « Décomposition de l'APY » de la Boucle (Aave et Morpho) montre en cascade d'où vient l'APY net : le rendement du collatéral (taux de dépôt + rendement propre du token, ou taux fixe d'un PT) × L, + Merkl (Aave) ou les récompenses d'emprunt (Morpho), − le coût de l'emprunt (taux + rendement propre d'un token de dette) × (L − 1), = APY net, puis − les coûts d'entrée et de sortie répartis sur la durée prévue (jusqu'à l'échéance pour un PT), = APY coûts compris. Barres vertes en hausse, rouges en baisse, totaux depuis zéro colorés comme tout APY (`tone.ts`). Les deux totaux sont ceux du résumé et des tuiles. Code : `src/domain/waterfall.ts`, `src/ui/Waterfall.tsx`, `src/features/loop/shared/ApyBreakdown.tsx`.

## Taux moyens sur 7 et 30 jours

Pour ne pas ouvrir une boucle sur un pic de taux, la Boucle montre la moyenne sur 7 et 30 jours des taux de dépôt et d'emprunt de la paire (bloc « Taux Aave »), l'APY net de la boucle à ces taux moyens (bloc « Risques ») et un bandeau ambre quand le taux d'emprunt dépasse 1,5 fois sa moyenne sur 30 jours et d'au moins un point (idem pour un rendement de dépôt en pic). Source : les événements `ReserveDataUpdated` du pool, qui portent les index de la réserve à chaque action. Le dernier événement avant la date de début donne l'index d'alors, `getReserveNormalizedIncome` / `getReserveNormalizedVariableDebt` celui d'aujourd'hui ; leur rapport, annualisé, est l'APY moyen (`src/protocols/aave/rateHistory.ts`). Il faut un RPC qui garde les logs de la période : PublicNode ne garde qu'environ un jour sur Ethereum, Arbitrum, Optimism, BNB et Linea, le RPC public suivant de la chaîne prend alors le relais ; sans historique lisible, la moyenne ne s'affiche pas.

## Historique 30 / 90 jours de l'APY

Pour distinguer un pic de deux jours d'un régime, le bloc « Historique » de la Boucle (Aave et Morpho) trace l'APY net de la boucle jour par jour sur 30 ou 90 jours, au levier choisi : taux de dépôt du collatéral × L − taux d'emprunt × (L − 1), plus le rendement propre du token et Merkl comptés à leur niveau du jour (leur historique n'est pas lu). Ligne pointillée : la moyenne de la période ; survol ou toucher : la valeur du jour ; les valeurs sont aussi dans un tableau pour les lecteurs d'écran. L'en-tête donne la moyenne sur 30 jours et signale un « pic du jour » quand l'APY d'aujourd'hui dépasse 1,5 fois cette moyenne et d'au moins 5 points (« creux » dans l'autre sens). Sources sans clé, CORS ouverts : l'API Aave (`supplyAPYHistory` / `borrowAPYHistory`, un taux moyen par jour sur six mois, `src/protocols/aave/rateSeries.ts`) et l'API Morpho (`historicalState.borrowApy`, `src/protocols/morpho/rateSeries.ts`). Calcul dans `src/domain/apyHistory.ts`, courbe dans `src/ui/LineChart.tsx`. Sans historique (SparkLend, marché Morpho lu sur la chaîne), le bloc n'apparaît pas.

## Ramener à un health factor cible

Chaque carte de l’écran Positions (Aave et Morpho) a un repli « Health factor cible » : une cible au choix (1,05 à 1,30 pour une paire corrélée, 1,25 à 2 sinon), gardée dans le navigateur pour cette position. Hors d’une bande autour de la cible (−0,01 / +0,03 pour une paire corrélée, −0,03 / +0,1 sinon), la carte propose « Ramener à … » : sous la cible, un bandeau ambre (rouge en zone de liquidation) dit combien de dette rembourser ; au-dessus, une ligne discrète dit combien emprunter de plus. Sans cible, seule la sécurité joue : une position sortie de la zone verte est ramenée à 1,10 (corrélée) ou 1,40, jamais poussée vers plus de levier. Le levier visé vient du health factor lui-même (seuil effectif = HF × dette / collatéral, puis L = HF / (HF − seuil)). Le bouton ouvre la Boucle préremplie, « Fermer / réduire » au levier visé (arrondi vers le bas, pour atteindre la cible) ou « Augmenter » sans nouveau capital ; la transaction se signe comme d’habitude, sans permission permanente (`src/domain/rebalance.ts`, `src/features/positions/HfTarget.tsx`). Testé le 13/11/2026 sur fork de Plasma (`node e2e/run.cjs rebalance`, `HF_TARGET='1,30'`) : HF 1,23 ramené à 1,29 avant l’arrondi vers le bas, corrigé depuis.

## Health factor projeté

Chaque carte de Positions (Aave et Morpho) donne en une ligne le health factor dans 30 et 90 jours si les prix ne bougent pas et que les taux restent ceux du jour (`src/domain/projection.ts`, `src/features/positions/HfProjection.tsx`, ajouté le 13/11/2026) : chaque actif déposé croît à son taux de dépôt plus son rendement propre (que son oracle suit), chaque dette à son taux d’emprunt plus le rendement d’une dette à rendement. Un PT sur Aave monte vers le pair au rythme de la décote annuelle de son flux de prix (lue dans le snapshot) ; sans flux connu (Morpho), il croît à son rendement fixe jusqu’à l’échéance, plus rien ensuite. Quand l’échéance d’un PT tombe avant 90 jours, la ligne donne aussi le health factor à l’échéance. C’est une information, pas une alerte : elle montre la dérive d’une boucle à écart négatif.

## La position en une image

Dans le résumé de la Boucle (Aave et Morpho) et sur chaque carte de Positions, une barre horizontale représente le collatéral : la dette en couleur du health factor (vert, ambre, rouge, seuils de `tone.ts`), la marge jusqu'au seuil de liquidation, un trait rouge au seuil (seuil pondéré du compte sur Aave, déduit de HF = collatéral × seuil / dette ; LLTV sur Morpho), puis la part qui ne peut jamais être empruntée, hachurée. Un repère noir marque la dette dans 90 jours aux taux du jour (même calcul que le health factor projeté), affiché quand il s'écarte de la dette actuelle. Légende en dessous : dette et marge en $, seuil en %. Dans « Risques », une courbe « Health factor selon le prix du collatéral face à la dette », de −20 % à +10 %, avec la ligne de liquidation (HF 1) et le point du jour. Sur mobile, la barre du résumé est masquée (barre collante réduite) ; celle des cartes reste. Code : `src/domain/positionBar.ts`, `src/ui/PositionBar.tsx`, courbe avec `src/ui/LineChart.tsx`.

## Gain réel et historique d’une position

Chaque carte de l’écran Positions (Aave et Morpho) a un repli « Gain réel » : ce que la position a vraiment gagné depuis son premier mouvement, en dollars et dans l’actif emprunté, le rendement réalisé annualisé (méthode de Dietz modifiée, pondérée par la durée de chaque apport) et la liste des transactions avec leur lien vers l’explorateur. Gain = valeur nette actuelle − apport net, l’apport net étant dépôts + remboursements − retraits − emprunts, chacun au prix de son jour. Sources, sans clé : l’API d’Aave (`userTransactionHistory`), l’API de Morpho (`marketTransactions`), les prix du jour de DefiLlama (`coins.llama.fi/batchHistorical`, à 6 h près ; à défaut, le prix oracle actuel, signalé). L’API d’Aave ne voit pas les aTokens que le contrat retire du compte à la fermeture ou au changement de collatéral : les reçus de ces transactions sont relus pour les ajouter (`src/features/positions/history.ts`). Un historique incomplet (plus de 1 000 mouvements, reçu illisible) n’affiche pas de gain. Le gas n’est pas compté. Vérifié le 12/11/2026 sur de vraies adresses de Base (Aave et Morpho) : l’historique Morpho retrouve exactement le collatéral et la dette empruntée de la position.

## Réclamer et réinvestir les rewards Merkl

Onglet « Réinvestir » de la Boucle (et bouton « Réinvestir » d'une position quand Merkl doit des rewards sur son réseau). Chaque étape est une transaction signée depuis le portefeuille, sans contrat nouveau ni autorisation durable (`src/protocols/aave/reinvest.ts`, `src/features/loop/aave/ReinvestPanel.tsx`) :
1. réclamer sur le Distributor de Merkl (`0x3Ef3D8bA38EBe18DB133cEc108f4D14CE00Dd9Ae`), une transaction pour tous les tokens du réseau. Le montant réclamable est le cumul de l'arbre moins le `claimed` lu on-chain sur le Distributor (l'API Merkl a des heures de retard) ;
2. pour chaque reward : l'aToken du collatéral est déjà du collatéral ; le collatéral lui-même devient du capital ; l'aToken d'une autre réserve est retiré d'Aave puis échangé ; tout autre token est échangé en collatéral par l'agrégateur, depuis le portefeuille (approbation du montant exact au routeur, minimum du devis vérifié sur le solde reçu). Moins de 1 $ ou prix inconnu : le token reste dans le portefeuille ;
3. « Augmenter la position » : l'onglet Ouvrir / augmenter s'ouvre avec ce capital et le levier qu'avait la position.

**En un clic** (portefeuille qui envoie un lot atomique, EIP-5792 `wallet_sendCalls` avec `forceAtomic` : MetaMask en compte intelligent, Ambire ; position à reprendre sur la paire ; eMode du compte compatible) : toutes les étapes partent en une confirmation, toutes passent ou aucune (`src/protocols/aave/batch.ts`). Garde-fous :
- le calldata de chaque échange est relu avant signature (`src/services/quotes/swapCalldata.ts`, Velora, KyberSwap et 1inch) : mêmes tokens, montant vendu exact (et jamais plus tiré par le routeur), sortie payée au portefeuille, aucun frais, minimum au moins celui de l'app ; sinon le devis est refusé. Ce contrôle vaut aussi pour le mode étape par étape ;
- le capital remis au contrat est la somme de ces minimums : si un échange rend moins, le contrat ne peut pas prendre le capital et tout le lot est annulé ;
- chaque autorisation (routeur, contrat, délégation de crédit) est du montant exact et revient à sa valeur d'avant juste après usage (0 le plus souvent) ; pour les tokens type USDT, passage par 0 ;
- devis, autorisations et levier recalculés au clic ; LTV projetée au pire cas vérifiée ; simulation du lot (`eth_simulateV1`) quand le RPC la permet, le portefeuille simule de son côté ;
- le contrat n'a pas changé : il ne vérifie toujours que son propre échange et n'agit que pour l'adresse qui signe.

Sinon, le mode étape par étape ci-dessus reste disponible.

Testé sur fork de Base le 05/11/2026 avec un compte réel qui avait 47 MORPHO à réclamer (`USER_ADDR=0x… node e2e/run.cjs reinvest r`) : réclamation, approbation, échange MORPHO → 0,0435 WETH, puis Augmenter prérempli. En un clic (portefeuille de test qui exécute le lot avec retour arrière en cas d'échec), sur une position WETH/USDC à 1,98x : réclamation, échange, levier en un lot ; collatéral +210 $, dette +103 USDC, levier inchangé, toutes les autorisations revenues à 0. Le Distributor n'a été vérifié que sur Base (même adresse annoncée par Merkl sur les autres réseaux).

## Ouvrir et fermer en une confirmation

Avec un portefeuille qui envoie des lots atomiques (EIP-5792, `forceAtomic` : MetaMask en compte intelligent, Ambire), « Ouvrir / augmenter » et « Fermer / réduire » partent en une seule confirmation (`openBatchCalls`, `closeBatchCalls` dans `src/protocols/aave/batch.ts`) :
- ouvrir : eMode si besoin, autorisation du capital et délégation d'emprunt au contrat pour les montants exacts, `open`, puis autorisation et délégation remises à leur valeur d'avant ;
- fermer : autorisation des aTokens exacte (0,1 % de marge sur une fermeture totale, les intérêts courent), `close`, puis autorisation remise à sa valeur.
Les autorisations sont relues au moment du clic, le lot est simulé quand le RPC le permet, et c'est le même appel au contrat que le mode habituel. Les tests (`batchOpenClose.test.ts`) vérifient qu'aucun lot ne laisse une autorisation plus grande qu'avant, quelle que soit la valeur de départ. Sans lot atomique, le mode habituel (signature de délégation ou permit, puis transaction) reste.
Testé sur fork de Base le 05/11/2026 : ouverture 3x de 1 WETH en un lot puis fermeture totale en un lot ; autorisation WETH, délégation USDC et autorisation aWETH à 0 après chaque lot, contrat sans solde.

## Montant en un geste

Sous « Capital » : le solde est cliquable (tout le solde), avec trois puces 25 / 50 / 100 %. Dans la liste des tokens du capital (contrat v2), ceux que le portefeuille détient viennent en premier, du plus gros au plus petit, avec leur valeur en $ au prix de l'oracle ; les deux tokens de la paire suivent même sans solde. Le token natif de la chaîne (ETH, XPL, MON…) y figure quand le marché liste sa version enveloppée (WETH, WXPL, WMON…) : il est converti par `deposit()` juste avant l'ouverture, dans le même lot atomique quand le portefeuille sait les envoyer (EIP-5792), sinon par une transaction de plus ; le WETH déjà détenu n'est pas touché. Le solde natif proposé garde 2 % pour le gas. Testé sur fork de Base depuis l'app le 13/11/2026 : 1 ETH en étapes, puis 0,5 ETH en lot (`CAPITAL=ETH` dans `e2e/run.cjs`). Code : `src/chain/walletTokens.ts` (ordre, entrée native), `CapitalField` dans `src/features/loop/shared/OpenFields.tsx`, `wrapNative` dans `src/protocols/aave/execute.ts` et `batch.ts`. Morpho garde son choix collatéral / token emprunté, avec les mêmes puces.

## eMode

Les catégories eMode du marché sont lues sur le pool (getters Aave v3.2+ : configuration, bitmaps collatéral, empruntable et LTV nulle). Pour une paire, l'interface propose les catégories où le collatéral compte avec la LTV de la catégorie et où la dette est empruntable, la meilleure LTV par défaut (ou la catégorie actuelle du compte si elle convient). Les calculs utilisent alors la LTV et le seuil de liquidation de la catégorie. L'eMode est un réglage du compte Aave que seul l'utilisateur peut changer : si besoin, une transaction `setUserEMode` part avant l'ouverture, le contrat ne change pas. La fermeture calcule avec l'eMode actuel du compte.

## Ce que fait l’interface

**Ouvrir** : emprunt `D = capital × (levier − 1)` au prix de l’oracle Aave, devis D → collatéral chez l’agrégateur choisi (taker = contrat), `minOut` = devis − slippage. Affiche collatéral déposé, levier effectif, health factor (attendu et pire cas), prix de liquidation, LTV face au maximum d’Aave, APY net. Bloque si la LTV dépasse le maximum, si l’actif est isolé, gelé, sans flash loan, ou si le solde manque.
Signature : `approve` du collatéral si besoin (une transaction, une fois), délégation de crédit signée en EIP-712 si besoin (sans gas), puis `openWithSig` ou `open`.

**Signaux de risque** (`src/domain/riskSignals.ts`, `src/features/loop/shared/RiskSignals.tsx`, ajouté le 13/11/2026) : en tête du repli « Risques » de l'ouverture (Aave et Morpho), des faits, chacun avec sa couleur, sans score global. « Marché / oracle » : prix actuel du collatéral contre la dette chez DefiLlama comparé à l'oracle (seul un marché sous l'oracle compte : c'est perdu à la sortie ; ambre dès 0,5 % pour une paire corrélée, 1 % sinon, l'oracle d'une paire volatile ayant son propre seuil de mise à jour). « Découplage passé » (paire corrélée) ou « Plus forte baisse » : plus forte baisse du rapport collatéral / dette sur 90 jours depuis son plus haut, cours DefiLlama toutes les 6 h (ambre dès 1 % pour une paire corrélée, 20 % sinon). « Sortie » : perte du devis de sortie à la taille de la position, le même que la garde de sortie. « Concentration » (Morpho, API) : part de la dette du marché tenue par le plus gros emprunteur. Un signal illisible est omis. Le résumé du repli nomme le pire signal non vert. Dans le Scanner, une paire corrélée dont le rapport a décroché d'1 % ou plus sur 90 jours (cours quotidiens, 500 points au plus par requête DefiLlama) porte l'étiquette « décroché −X % sur 90 j ». Non fait : le type d'oracle (taux fixe, CAPO), qui demanderait de lire chaque adaptateur.

**Sortie vérifiée avant d'ouvrir** (`src/domain/exitCheck.ts`, Aave et Morpho, tout collatéral hors PT qui a son propre contrôle) : l'app cote aussi la vente du collatéral qu'une fermeture totale vendrait (la dette entière après l'ouverture, au prix de l'oracle, + 1 %, arrondi au-dessus) contre l'actif de la dette. Aucune route (devis en échec ou seulement simulé) : l'ouverture est bloquée, l'app ne pourrait pas fermer la position. Une sortie qui perd plus de 0,5 % au prix de l'oracle, ou un collatéral dont la réserve Aave est empruntée à 98 % ou plus (son retrait à la fermeture peut devoir attendre), donne un avertissement.

**Capital dans n’importe quel token** (contrat v2) : une liste à côté du montant propose le collatéral, l’actif emprunté, puis les tokens du marché Aave que le wallet détient. L’actif emprunté est vendu avec l’emprunt dans le même swap ; un autre token est d’abord échangé contre le collatéral par le contrat (`capitalSteps`, devis capital → collatéral avec le contrat comme taker). L’emprunt vise le levier sur la valeur du capital (devis attendu, ou oracle pour l’actif emprunté) ; le health factor du pire cas et la garde utilisent les minimums des deux devis ; le coût d’entrée compte les deux swaps. L’autorisation porte sur le token du capital.

**Fermer / réduire** (25, 50, 75 % ou tout) : avec la v2, le flash loan vient de Morpho Blue (sans prime) quand il détient au moins 102 % du montant à rembourser, sinon d'Aave (prime). Calcule le collatéral à vendre pour couvrir dette + prime éventuelle + slippage, vérifie que le minimum garanti du devis couvre le remboursement, affiche ce qui revient. Permit d’aToken signé si besoin, puis `closeWithSig` ou `close`.

**Changer de dette** (contrat v2 à partir du 13/11/2026, onglet visible quand le compte a une dette sur la paire) : nouvel actif de dette parmi ceux empruntables du marché (actifs, ni gelés ni en pause, ceux de la catégorie eMode du compte s’il en a une), classés du moins cher au plus cher (taux d’emprunt + rendement propre − récompense Merkl), par défaut le moins cher de la même famille (un stable pour un stable). Part de 25 %, 50 % ou tout. Le contrat emprunte la nouvelle dette en flash loan Aave mode 2 (sans prime), la vend contre l’ancienne et rembourse celle-ci (`swapDebt`) ; le collatéral ne bouge pas. Pour tout changer, le montant vendu est recalé sur un premier devis pour que le minimum garanti couvre la dette + 0,05 % (intérêts jusqu’à l’inclusion), le contrat rembourse la dette exacte et le surplus revient au wallet. Contrôles : liquidité et plafond d’emprunt du nouvel actif, health factor après (garde à 98 %), perte du swap ; avertissements si le nouvel actif n’est pas moins cher ou n’évolue pas avec l’ancien. Affiche l’économie par an aux taux actuels et le nombre de jours pour rembourser le coût. Délégation de crédit signée si besoin puis `swapDebtWithSig`, ou lot avec délégation exacte. Un contrat v2 déployé avant cette fonction reste utilisable pour le reste ; l’onglet propose alors de déployer le contrat actuel (adresse commune). Testé le 13/11/2026 sur fork de Plasma (`node e2e/run.cjs debt`, `TARGET=USDT0`) : déploiement du contrat depuis l’app, ouverture 4x de 1 000 USDe sur GHO, dette GHO entièrement passée en USDT0 (2 996,10 GHO remboursés, 3 027,61 USDT0 empruntés au slippage de 1 %, 32 GHO rendus), puis 50 % repassés en GHO.

**Changer de collatéral** (contrat v2, onglet visible quand le compte a du collatéral sur la paire) : nouveau collatéral parmi ceux du marché acceptés comme collatéral (LTV > 0, ni gelés, ni en pause, ni isolés ; ceux de la catégorie eMode du compte s’il en a une), part de 25 %, 50 % ou tout. Devis ancien → nouveau collatéral (taker = contrat) ; le contrat emprunte en flash loan `minOut − prime` du nouveau collatéral (Morpho sans prime s’il en détient au moins 102 %, sinon Aave), le dépose, retire l’ancien, l’échange et rembourse ; le surplus est déposé aussi. Health factor projeté avec le seuil de chaque collatéral, garde à 98 % du pire cas, APY avant / après, coût (swap, prime, gas). Permit d’aToken signé si besoin puis `swapCollateralWithSig`, ou lot avec autorisation exacte. Après un changement partiel, le compte a deux collatéraux : les écrans comptent alors le levier sur tout le compte, et « Fermer » refuse de rembourser plus que le collatéral de la paire ne couvre (réduire moins, ou ramener d’abord tout le collatéral sur un seul). La dette ne change pas ; après un changement total, le reste d’intérêts de l’ancien collatéral non vendu revient au wallet.

**Montants réels** (contrat v2) : après chaque ouverture, augmentation, réduction, fermeture ou changement de collatéral, l’app lit le reçu et décode les événements du contrat (`PositionOpened`, `PositionClosed`, `CollateralSwapped`, un `Swapped` par swap), pour le seul contrat Auto-loop et le compte connecté. Sous la ligne de succès, la liste « Montants réels » donne capital, déposé, emprunté, remboursé, retiré, rendu, prime (si non nulle), chaque swap et le health factor final ; « (devis …) » s’ajoute quand le réel s’écarte de plus de 0,01 % de l’estimation. Dans un lot, le reçu pris est celui où le contrat a agi. Rien n’est affiché si le reçu est illisible ou avec un contrat v1.

Avant chaque signature : nouvelle cotation (un devis expire en quelques blocs), simulation `eth_call` de la transaction, erreurs du contrat traduites. Le domaine EIP-712 est recalculé et comparé au `DOMAIN_SEPARATOR` du token avant de signer.

## Velora

Chaque appel (`/prices` et `/transactions`) passe `partner=auto-loop` : sans ce paramètre, l’API publique ajoute 1 bp de frais « anon ». L’interface refuse un devis si `partnerFee` n’est pas nul ou si le calldata Augustus v6.2 encode des frais (champ `partnerAndFee`, vérifié sur de vrais devis : 1 bp sans `partner`, 0 avec). Le montant affiché est `destAmountAfterFee` quand Velora le fournit.

## Test de bout en bout sur fork de Base

Depuis le 10/11/2026 l'app s'ouvre sur le Scanner (ou sur Positions quand un portefeuille se reconnecte) et chaque écran a son adresse (`#boucle`, `#scanner`, `#positions`) : `run.cjs` ouvre `#boucle`. Le contrat manquant se déploie par le bouton du résumé, qui enchaîne connexion, réseau, déploiement puis l'action de l'écran. Testé le 10/11/2026 sur fork : déploiement par ce bouton, ouverture 3x de 1 WETH, réduction à 2x et fermeture totale (`AGG=Velora SLIP='0,5 %'` à l'époque ; depuis le 12/11/2026 le choix 0,5 % n'existe plus, prendre `SLIP='1 %'`).

Testé le 01/11/2026 avec le contrat sans owner : déploiement par le bouton de l'app (`NO_DEPLOY=1 bash e2e/fork.sh`, puis `node e2e/run.cjs deploy d`), puis ouverture 3x et fermeture totale avec ce contrat (`EXECUTOR=0x… node e2e/run.cjs open o`). Une adresse qui n'est pas le contrat (ex. WETH) est refusée.

Testé le 18/10/2026 : anvil sur fork de Base, contrat déployé sur le fork avec seulement le routeur Velora en liste blanche, interface dans Chromium avec un portefeuille de test (compte anvil 1), vraies lectures Aave v3 et vrais devis Velora.

```bash
anvil --fork-url https://mainnet.base.org --chain-id 8453     # terminal 1
bash e2e/fork.sh                                              # re-fork, déploiement, 1,5 WETH au compte de test
cat > .env.local <<'ENV'
VITE_EXECUTOR_ADDRESS=0x33dd750d10F53475A1FbF5e079a02BF0F74C3646
VITE_RPC_URL=http://127.0.0.1:8545
VITE_QUOTE_MODE=live
VITE_VELORA_INCLUDE_DEXS=UniswapV3,UniswapV4,AerodromeSlipstream,AerodromeSlipstreamFactory3,PancakeswapV3
ENV
npm run dev                                                   # terminal 2
NODE_PATH=$(npm root -g) node e2e/run.cjs open ouvrir         # puis reduce / close
```

Résultats (1 WETH de capital, levier 3x, dette USDC, slippage 0,5 %) :
- ouverture : approve, délégation de crédit signée en EIP-712, `openWithSig`. 4 750 USDC empruntés, 3,0 WETH déposés, HF 1,24 comme affiché, ~733k gas ;
- fermeture à 50 % puis totale : permit d’aWETH signé, `closeWithSig`. Dette à 0, ~1,7M gas pour la fermeture totale ; il revient 0,9835 WETH + 33,6 USDC, soit ~0,25 % de coût aller-retour sur le capital (swaps sur 3x le capital + prime de flash loan) ;
- après chaque transaction, le contrat ne garde ni token ni approval ;
- avec le filtre AMM, 3 tours complets sur 4 ont réussi (dont un avec fermeture à 50 %) ; l’échec est remonté comme une erreur dans l’interface, sans perte.

Testé le 08/11/2026 avec la v2 (`bash e2e/fork.sh` la déploie, `V1=1` déploie l'ancienne) : ouverture 3x, augmentation à 4x, réduction à 2x, fermeture totale via Morpho (prime 0, événement `PositionClosed` vérifié), en étapes et en lot (`BATCH=1`), avec Velora et KyberSwap ; déploiement par le bouton de l'app ; ouverture et fermeture avec un contrat v1 (bandeau de mise à jour affiché). Capital dans un autre token (`FUND=1 bash e2e/fork.sh` donne aussi 5000 USDC et 1 wstETH, puis `CAPITAL=USDC AMOUNT=2000` ou `CAPITAL=wstETH AMOUNT=0.5` pour `run.cjs open`) : ouverture 3x avec 2000 USDC, avec 0,5 wstETH (étapes et lot), augmentation à 4x avec 1000 USDC. Changement de collatéral (`TARGET=cbETH PART="50 %" run.cjs swap`, `COLL=cbETH` pour agir ensuite sur la paire cbETH/USDC) : WETH → cbETH à 50 % via Morpho, en totalité en lot, en totalité via Aave (Morpho vidé de son cbETH sur le fork, prime prélevée), puis fermeture de la position cbETH/USDC. Montants réels : affichés après ouverture (capital wstETH, en lot), réduction, changement de collatéral et fermeture, identiques aux événements lus avec `cast`. La v2 ajoute un health factor minimum (98 % du pire cas du devis) et une échéance de 20 minutes à chaque appel.

Limite propre au fork : le fork est figé au bloc du `fork.sh`, alors que Velora cote sur l’état réel du moment. Les DEX à prix d’oracle (Kipseli, Tessera, WooFiV2, metric-v1…) revertent alors systématiquement, d’où `VITE_VELORA_INCLUDE_DEXS` limité aux AMM classiques. Même ainsi, une route peut encore échouer à la simulation si le fork a trop vieilli : relancer `fork.sh`. Sur le vrai réseau ce décalage n’existe pas, et de toute façon la simulation avant signature bloque une transaction qui échouerait.

## Test hebdomadaire sur fork

`.github/workflows/weekly-fork.yml` (ajouté le 13/11/2026) tourne chaque lundi à 6 h UTC et à la demande (onglet Actions, « Run workflow »), sans secret :

- `node e2e/api-check.mjs` appelle chaque API extérieure comme l'app le fait (Velora et KyberSwap : devis puis transaction, Pendle, Morpho, Merkl, DefiLlama prix et historique) et vérifie les champs lus ;
- sur un fork de Base (1 WETH à 3x contre USDC) et un de Plasma (1 000 USDe à 3x contre GHO) : déploiement du contrat commun avec le bouton de l'app, ouverture puis fermeture avec de vrais devis, par `e2e/run.cjs` avec `E2E_STRICT=1` (code de sortie 1 si le bouton reste grisé ou si la transaction ne finit pas en succès). Un essai de plus après deux minutes, les agrégateurs limitant le débit par adresse IP.

Un échec ouvre un ticket GitHub « Test hebdomadaire sur fork en échec » (ou le commente s'il est déjà ouvert), avec le lien vers le run et ses captures ; le premier succès suivant le ferme. Le portefeuille de test de `run.cjs` ajoute 30 % à l'estimation de gas, comme un vrai portefeuille : l'estimation nue d'anvil ne suffit pas toujours aux routes KyberSwap.

## Organisation du code

Chaque dossier de `src/` a un rôle unique ; les dépendances vont de haut en bas (une fonctionnalité utilise les protocoles, jamais l'inverse).

| Dossier | Rôle |
|---|---|
| `app/` | Coquille : `App.tsx` (vues, adresse de la page, choix du réseau), bouton portefeuille, `wallets.ts` (EIP-6963). |
| `features/scanner/` | Écran Scanner : `Scanner.tsx`, lignes Aave (`aaveScan.ts`) et Morpho (`morphoScan.ts`), regroupement, montant (`sizing.ts`), filtres retenus (`prefs.ts`). |
| `features/loop/aave/` | Écran Boucle Aave : `AaveView.tsx`, `AaveOpenPanel`, `AaveClosePanel`, `SwapCollateralPanel`, `ReinvestPanel`. |
| `features/loop/morpho/` | Écran Boucle Morpho : `MorphoView.tsx`, `MorphoOpenPanel`, `MorphoClosePanel`, `MorphoRollPanel`. |
| `features/loop/shared/` | Blocs communs aux deux : risques, campagnes Merkl, prix du PT, déploiement du contrat, choix du token. |
| `features/positions/` | Écran Positions : positions Aave et Morpho, historique et gain réel (`history.ts`). |
| `protocols/aave/` | Lecture du marché (`useMarket.ts`, `snapshot.ts`, `rateHistory.ts`), plans et envoi des transactions (`execute.ts`, `batch.ts`, `signatures.ts`, `swapCollateral.ts`, `swapDebt.ts`), réinvestissement Merkl (`reinvest*.ts`). |
| `protocols/morpho/` | Marchés (API vérifiée on-chain, `markets.ts`), appels du contrat Morpho (`execute.ts`). |
| `protocols/pendle/` | PT : marchés, devis RouterStatic, calldata du routeur, échéances (`pt.ts`). |
| `services/` | Données tierces : devis Velora / KyberSwap / 1inch (`quotes/`), Merkl, rendement propre des tokens (`yield/`). |
| `domain/` | Calculs purs, sans réseau : levier et health factor (`math.ts`), coûts et seuil de rentabilité (`economics.ts`), courbes de taux (`irm.ts`), slippage, contrôle de sortie, familles d'actifs (`pairs.ts`). |
| `chain/` | Portefeuille et contrats : ABI, config wagmi, déploiement CREATE2, lots EIP-5792 (`batch.ts`), erreurs lisibles (`tx.ts`), soldes du portefeuille, lecture du résultat d'une transaction. |
| `ui/` | Composants de la charte (`primitives.tsx`, `Picker`, bouton de résumé `gate.tsx`), formats (`format.ts`) et couleurs (`tone.ts`). |
| `config/` | Un fichier par sujet : marchés Aave, réseaux Morpho, Pendle, agrégateurs, RPC, contrats, variables d'environnement. |
| `generated/` | Bytecode des contrats, écrit par `contracts/script/export-bytecode.cjs`. Ne pas modifier à la main. |
| `test/` | Données et aides de test partagées. Les tests unitaires sont à côté de leur fichier (`x.test.ts`). |
| `e2e/` (hors `src/`) | Test de bout en bout sur fork : `fork.sh` (re-fork, déploiement, fonds de test), `run.cjs` (Chromium + portefeuille de test). |

Qualité : `npm run lint` (eslint), `npm run format:check` (prettier), `npm test` (vitest), `npm run typecheck` ; les quatre passent en CI avant chaque publication.
